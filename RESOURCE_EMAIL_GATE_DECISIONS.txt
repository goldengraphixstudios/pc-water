OVERVIEW
--------
The resource download gate captures a visitor's email before allowing them to
download any of the 7 free PDF guides. Emails are stored in the Supabase
`resource_leads` table and visible in the CMS at /cms/leads.


--------------------------------------------------------------------------------
HOW VALIDATION IS CURRENTLY LAYERED (4 layers)
--------------------------------------------------------------------------------

Layer 1 — FORMAT CHECK (always active, instant)
  >> Regex: /^[^\s@]+@[^\s@]+\.[^\s@]{2,}$/
  >> Catches: obvious non-emails (no @, no domain, etc.)
  >> Limitation: does not confirm the domain or mailbox exists

Layer 2 — DISPOSABLE DOMAIN BLOCKLIST (always active, instant)
  >> Hardcoded list of ~35 known temp-mail services
     (mailinator, yopmail, guerrillamail, tempmail, trashmail, 10minutemail, etc.)
  >> Catches: people using throwaway inboxes
  >> Limitation: new disposable services appear constantly; list needs updating

Layer 3 — ROLE ADDRESS BLOCK (always active, instant)
  >> Blocks prefixes: noreply, no-reply, donotreply, postmaster, bounce, mailer-daemon
  >> Catches: shared / system mailboxes that no real person monitors
  >> Limitation: only blocks exact known prefixes

Layer 4 — ABSTRACT API MX + DELIVERABILITY CHECK (active only if API key is set)
  >> Calls: https://emailvalidation.abstractapi.com/v1/
  >> Checks:
       - Is the email domain real and configured to receive mail? (MX record)
       - Is the email SMTP-reachable? (mailbox ping)
       - Is it a disposable service? (their database, updated continuously)
       - Is it a role address (admin@, info@, etc.)?
       - Deliverability score: DELIVERABLE / UNDELIVERABLE / RISKY / UNKNOWN
  >> If UNDELIVERABLE → blocked with message
  >> If no MX record → blocked with message
  >> If API times out or errors → silently allowed through (never blocks real users due to API issues)
  >> Free tier: 100 requests/month
  >> Paid: $9/month for 1,000 requests, $19/month for 10,000


--------------------------------------------------------------------------------
HOW TO ENABLE ABSTRACT API (strongly recommended)
--------------------------------------------------------------------------------

1. Sign up at: https://www.abstractapi.com/api/email-verification-validation-api
2. Copy your API key from the dashboard
3. Add to .env.local in the website root:

   NEXT_PUBLIC_ABSTRACT_EMAIL_API_KEY=your_api_key_here

4. Also add the same variable to your GitHub repository secrets for the
   GitHub Actions deploy (Settings > Secrets and variables > Actions):

   NEXT_PUBLIC_ABSTRACT_EMAIL_API_KEY = your_api_key_here

5. Redeploy the site — the Settings panel in /cms/leads will show "Active"
   next to Email Verification once it's working.

Without the API key, Layers 1–3 still run. With it, all 4 layers run.

FUTURE VERIFICATION OPTIONS (if higher quality leads become a priority)
--------------------------------------------------------------------------------

OPTION A — Double opt-in (highest lead quality, more friction)
  >> Flow: visitor submits email → they receive a confirmation email with a
     unique link → they click the link → download becomes accessible
  >> Guarantees the person owns and can access the inbox
  >> Requires an email-sending service: Resend (resend.com) is recommended
     - Free tier: 3,000 emails/month, 100/day
     - Integration: Resend API, called via a Supabase Edge Function or a
       minimal API route (would need to move away from static export)
  >> Complexity: medium (needs a unique token table, email template, verify route)
  >> Tradeoff: conversion rate drops ~20–40% vs soft gate, lead quality improves

OPTION B — Supabase Edge Function proxy (best coverage, no CORS risk)
  >> Move the email validation call server-side into a Supabase Edge Function
  >> Can use heavy validation libraries (mailcheck.js, etc.) without CORS concern
  >> Abstract API key stays private (not exposed as NEXT_PUBLIC_*)
  >> Complexity: low-medium (write one edge function, update the gate to POST to it)
  >> Recommended if Abstract API is configured and the secret key exposure in
     the browser is a concern (NEXT_PUBLIC_ keys are visible in the browser bundle)

OPTION C — Upgrade to Next.js server runtime (removes static export constraint)
  >> Currently the site uses `output: 'export'` for GitHub Pages compatibility
  >> Switching to a server runtime (Vercel, Railway, Fly.io) enables:
       - Server-side email validation (keeps API key private)
       - Signed download URLs (time-limited, can't be shared)
       - Full double opt-in without edge functions
       - Webhook endpoints for form submissions
  >> Tradeoff: leaves GitHub Pages free hosting; paid hosting required

CMS LEADS PANEL — FEATURES SUMMARY (/cms/leads)
--------------------------------------------------------------------------------

Stats row:
  >> Total Leads — all time count
  >> Unique Emails — deduplicated count (same person downloading multiple guides counts once)
  >> This Week — leads in last 7 days
  >> Top Resource — resource with most downloads + its count

Resource breakdown:
  >> Bar chart showing all resources sorted by download count
  >> Visual comparison of which guides are most valuable to leads

Filters:
  >> Search by email or resource title
  >> Filter by division (All / PC Tanks / PC Water Solutions)

Settings panel (toggle):
  >> Export CSV — exports currently filtered/searched results as a dated CSV file
  >> Verification status — shows which layers are active, API key configuration status
  >> Validation layer cards — visual checklist of what is and isn't active

Table:
  >> Email, Resource, Division, Timestamp
  >> Respects active filters before rendering


--------------------------------------------------------------------------------
SUPABASE TABLE — resource_leads
--------------------------------------------------------------------------------

Column         Type          Notes
----------     -----------   --------------------------------------------------
id             uuid          auto-generated primary key
email          text          validated email address
resource_slug  text          e.g. "tank-maintenance-checklist"
resource_title text          e.g. "Tank Maintenance Checklist"
division       text          "PC Tanks" or "PC Water Solutions"
downloaded_at  timestamptz   auto-set on insert (UTC)

RLS policies:
  >> INSERT: anyone (public, no auth required — allows the gate to work)
  >> SELECT: authenticated users only (CMS admins via Supabase Auth)

SQL to create (run in Supabase SQL Editor if not yet created):

  CREATE TABLE IF NOT EXISTS public.resource_leads (
    id             uuid        DEFAULT gen_random_uuid() PRIMARY KEY,
    email          text        NOT NULL,
    resource_slug  text        NOT NULL,
    resource_title text,
    division       text,
    downloaded_at  timestamptz DEFAULT now()
  );

  ALTER TABLE public.resource_leads ENABLE ROW LEVEL SECURITY;

  CREATE POLICY "Anyone can submit lead"
    ON public.resource_leads FOR INSERT WITH CHECK (true);

  CREATE POLICY "Authenticated can read leads"
    ON public.resource_leads FOR SELECT USING (auth.role() = 'authenticated');

NOTES
--------------------------------------------------------------------------------

>> The `cms-media` Supabase bucket is PUBLIC — files are accessible without
   authentication via their public URL. The email gate is a SOFT gate: it
   collects the email and then provides the public URL. A determined person
   can bypass it by guessing the URL. This is acceptable for lead generation
   (most people won't bother, and the files aren't confidential). If the
   content ever becomes sensitive, move to signed URLs via a server runtime.

>> The Abstract API key is a NEXT_PUBLIC_ variable, meaning it is visible in
   the browser JavaScript bundle. This is a known tradeoff of static site
   architecture. The key only has permission to call the email validation
   endpoint; it cannot be used to access private data. If this is a concern,
   move the call to a Supabase Edge Function (see Option B above).
